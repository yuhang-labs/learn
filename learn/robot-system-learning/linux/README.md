## 3. 重点理解

### 路径

- 绝对路径从 `/` 开始，不依赖当前目录。
- 相对路径以当前目录为起点。
- `.` 表示当前目录，`..` 表示上一级目录。
- `pwd` 默认显示 Shell 维护的逻辑路径；`pwd -P` 会解析符号链接并显示物理路径。路径中没有符号链接时，两者结果可能相同。

### 重定向

- 标准输出的文件描述符是 `1`，用于正常结果。
- 标准错误的文件描述符是 `2`，用于错误和诊断信息。
- `>` 或 `1>` 将标准输出覆盖写入文件。
- `>>` 将标准输出追加到文件末尾。
- `2>` 将标准错误写入文件。
- `2>&1` 让标准错误使用标准输出当前指向的位置。
- `ls > list.txt 2> err.txt` 执行成功时，`err.txt` 为空是正常现象，因为命令没有产生标准错误。
- 重定向可以保存程序运行日志，方便后续检查和定位问题。

### 文本处理

- `grep` 根据条件筛选行，`grep -n` 还会显示行号。
- `sort` 对文本行进行排序，不负责筛选内容。
- `uniq` 合并相邻的重复行，通常与 `sort` 组合使用：`sort file | uniq`。
- `sed -n '1,5p' file` 显示文件第 1 到第 5 行。
- `grep 't*'` 中的 `*` 是正则量词，表示前面的 `t` 出现零次或多次，因此它可能匹配不含 `t` 的行。查找具体文本可使用 `grep 'third' file`。

### Shell 变量和参数

- 普通 Shell 变量默认只属于当前 Shell。
- 使用 `export` 导出的环境变量可以被当前 Shell 启动的子进程继承。
- `$HOME` 保存当前用户的主目录。
- `$PATH` 保存命令搜索目录，多个目录使用 `:` 分隔。
- 变量可以写成 `$name` 或 `${name}`；为避免空格和通配符造成拆分，通常使用 `"$name"`。
- `$0` 是脚本名称，`$1`、`$2` 是第一、第二个位置参数，`"$@"` 表示全部位置参数。
- 执行 `./day3_args.sh robot linux` 时，`robot` 对应 `$1`，`linux` 对应 `$2`。
- `-gt`、`-lt`、`-eq` 分别表示整数大于、小于和等于。
- `while` 在条件成立时继续循环；`until` 在条件成立时结束循环。

### Git 工作区域

- 工作区是正在编辑的文件。
- 暂存区保存下一次提交准备包含的版本，由 `git add` 更新。
- `git commit` 将暂存区内容保存为本地仓库中的提交。
- `git push` 只是把本地提交同步到远程仓库，不是进入提交区的条件。

## 4. 遇到的问题与纠正

### `git restore` 恢复什么

- 默认的 `git restore file` 使用暂存区版本覆盖工作区文件。
- 已被 Git 跟踪的文件不需要在每次恢复前重新执行 `git add`。
- 如果先修改文件并执行 `git add`，随后又继续修改，那么 `git restore file` 会恢复到刚刚暂存的版本。
- 未跟踪文件没有 Git 保存的基准版本，因此普通的 `git restore` 无法恢复它。
- `git restore` 会丢弃工作区修改，执行前应先查看 `git diff`，避免误删有效内容。

### `git stash` 的“保存现场”和“后续恢复”

- “保存现场”是把尚未提交的已跟踪文件修改暂存到 stash，使工作区暂时恢复干净，便于切换任务或分支。
- `git stash list` 用于查看已经保存的现场。
- `git stash pop` 会重新应用最近的现场，并在成功后删除对应的 stash 记录。
- 普通 `git stash` 默认不包含未跟踪文件；需要同时保存未跟踪文件时使用 `git stash -u`。
- 本次练习中的 `temp.txt` 在 stash 后仍显示为未跟踪文件，说明它没有被普通 `git stash` 保存；实际保存的是当时已被 Git 跟踪的文件修改。

### 磁盘、内存和负载

### 诊断脚本验证

- 默认输出文件运行成功，六个依赖命令均显示 `[OK]`，脚本返回 `0`。

- 使用 `DAY4_TEST_MISSING=1` 注入不存在的命令后，脚本输出 `[ERROR]` 并返回 `1`。

## 3. 重点理解

### 文件类型、元数据和 inode

- `file` 主要回答“这个文件的内容属于什么类型”。
- `stat` 主要回答“这个文件在文件系统中具有什么属性”。
- 文件名是目录项中的名称，目录项把文件名关联到 inode。
- inode 保存文件的核心元数据，同一个 inode 可以通过多个硬链接文件名访问。
- `Unicode text, UTF-8 text` 表示文本包含 Unicode 字符并使用 UTF-8 编码，不表示它是二进制程序。

### 内核、发行版和架构

- Linux 严格来说是内核。
- Ubuntu 是基于 Linux 内核构建的完整发行版，包含系统工具、软件包管理、服务和可选桌面环境，不只是操作界面。
- `x86_64` 主机为 `aarch64` 目标构建程序时，通常需要对应的交叉编译工具链。

### 磁盘与内存

- `df` 的统计对象是文件系统，适合查看某个挂载点还剩多少空间。
- `du` 的统计对象是指定文件或目录，适合查看它实际占用多少磁盘空间。
- `free` 表示当前完全空闲的内存。
- `available` 还考虑系统可回收的缓存，更适合估计在不发生明显交换时还能提供给程序的内存。

### 平均负载

- `uptime` 的三个负载值依次对应过去 1、5、15 分钟。
- 负载统计处于可运行状态或不可中断睡眠状态的平均任务数，不是 CPU 百分比。
- 负载需要结合逻辑 CPU 数判断。例如负载 `4.0` 在 4 核系统上可能接近满载，在 16 核系统上通常仍有较多余量。

### Shell 状态和参数

- `$?` 只保存上一条命令的退出状态；执行新命令后会立即被覆盖，所以必须及时检查。
- `echo hello` 是有效的 Shell 内置命令，成功后会把 `$?` 改为 `0`。
- `${1:-day4_system_check.log}` 表示：第一个参数未设置或为空时使用默认日志名，否则使用第一个参数。
- `local command_name` 将变量限制在当前函数内，避免影响函数外的同名变量。
- `return 0` 或 `return 1` 结束当前函数，并向调用者返回成功或失败状态。
- `exit 1` 结束整个脚本，而不只是结束当前函数。
- `check_command "$command_name" || exit 1` 表示只有命令检查失败时，才以状态 `1` 终止脚本。
- `>&2` 把错误文字写入标准错误，便于将正常结果和错误信息分开处理。

## 4. 诊断脚本的执行流程

`day4_system_check.sh` 是一个最小系统诊断工具，流程如下：

1. 根据第一个参数决定日志名称；没有参数时使用默认名称。
2. 检查 `date`、`uname`、`hostname`、`df`、`free`、`uptime` 六个依赖命令。
3. 如果缺少依赖，向标准错误输出原因并以状态 `1` 结束，不生成不完整报告。
4. 如果依赖完整，收集主机、内核、架构、磁盘、内存和负载信息。
5. 将系统信息写入日志，并告诉用户日志保存位置。

## 5. 遇到的问题、根因与解决

### 脚本没有执行权限

- 现象：运行脚本时提示“权限不够”。
- 根因：脚本最初没有执行权限。
- 解决：使用 `chmod +x day4_system_check.sh` 添加执行权限。

### 相对路径使用错误

- 现象：在 `robot-system-learning/linux` 目录中再次使用 `robot-system-learning/linux/day4_system_check.sh`，提示文件不存在。
- 根因：相对路径从当前目录开始计算，重复写入了目录层级。
- 解决：已经位于脚本目录时直接使用 `./day4_system_check.sh`。

### 命令输入错误

- `at day4_custom.log` 应为 `cat day4_custom.log`。
- `;s` 不是有效命令，分号出现在没有前置命令的位置会产生语法错误。

### `echosss` 导致日志内出现错误

- 现象：日志中出现 `echosss: 未找到命令`，但脚本仍可能返回 `0`。
- 根因：`echosss` 在 Shell 语法上可以作为命令名，因此 `bash -n` 不会报语法错误；运行时才会发现命令不存在。后续的 `uptime` 成功又让命令组最终返回成功状态。
- 解决：将 `echosss` 修正为 `echo`，重新执行正常和异常验证。
- 经验：语法检查通过不等于运行逻辑正确，还必须检查日志、退出状态和产出文件。
