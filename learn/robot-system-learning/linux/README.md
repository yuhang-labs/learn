## 3. 重点理解

### 路径

- 绝对路径从 `/` 开始，不依赖当前目录。
- 相对路径以当前目录为起点。
- `.` 表示当前目录，`..` 表示上一级目录。
- `pwd` 默认显示 Shell 维护的逻辑路径；`pwd -P` 会解析符号链接并显示物理路径。路径中没有符号链接时，两者结果可能相同。

### 重定向

- 标准输出的文件描述符是 `1`，用于正常结果。
- 标准错误的文件描述符是 `2`，用于错误和诊断信息。
- `>` 或 `1>` 将标准输出覆盖写入文件。
- `>>` 将标准输出追加到文件末尾。
- `2>` 将标准错误写入文件。
- `2>&1` 让标准错误使用标准输出当前指向的位置。
- `ls > list.txt 2> err.txt` 执行成功时，`err.txt` 为空是正常现象，因为命令没有产生标准错误。
- 重定向可以保存程序运行日志，方便后续检查和定位问题。

### 文本处理

- `grep` 根据条件筛选行，`grep -n` 还会显示行号。
- `sort` 对文本行进行排序，不负责筛选内容。
- `uniq` 合并相邻的重复行，通常与 `sort` 组合使用：`sort file | uniq`。
- `sed -n '1,5p' file` 显示文件第 1 到第 5 行。
- `grep 't*'` 中的 `*` 是正则量词，表示前面的 `t` 出现零次或多次，因此它可能匹配不含 `t` 的行。查找具体文本可使用 `grep 'third' file`。

### Shell 变量和参数

- 普通 Shell 变量默认只属于当前 Shell。
- 使用 `export` 导出的环境变量可以被当前 Shell 启动的子进程继承。
- `$HOME` 保存当前用户的主目录。
- `$PATH` 保存命令搜索目录，多个目录使用 `:` 分隔。
- 变量可以写成 `$name` 或 `${name}`；为避免空格和通配符造成拆分，通常使用 `"$name"`。
- `$0` 是脚本名称，`$1`、`$2` 是第一、第二个位置参数，`"$@"` 表示全部位置参数。
- 执行 `./day3_args.sh robot linux` 时，`robot` 对应 `$1`，`linux` 对应 `$2`。
- `-gt`、`-lt`、`-eq` 分别表示整数大于、小于和等于。
- `while` 在条件成立时继续循环；`until` 在条件成立时结束循环。

### Git 工作区域

- 工作区是正在编辑的文件。
- 暂存区保存下一次提交准备包含的版本，由 `git add` 更新。
- `git commit` 将暂存区内容保存为本地仓库中的提交。
- `git push` 只是把本地提交同步到远程仓库，不是进入提交区的条件。

## 4. 遇到的问题与纠正

### `git restore` 恢复什么

- 默认的 `git restore file` 使用暂存区版本覆盖工作区文件。
- 已被 Git 跟踪的文件不需要在每次恢复前重新执行 `git add`。
- 如果先修改文件并执行 `git add`，随后又继续修改，那么 `git restore file` 会恢复到刚刚暂存的版本。
- 未跟踪文件没有 Git 保存的基准版本，因此普通的 `git restore` 无法恢复它。
- `git restore` 会丢弃工作区修改，执行前应先查看 `git diff`，避免误删有效内容。

### `git stash` 的“保存现场”和“后续恢复”

- “保存现场”是把尚未提交的已跟踪文件修改暂存到 stash，使工作区暂时恢复干净，便于切换任务或分支。
- `git stash list` 用于查看已经保存的现场。
- `git stash pop` 会重新应用最近的现场，并在成功后删除对应的 stash 记录。
- 普通 `git stash` 默认不包含未跟踪文件；需要同时保存未跟踪文件时使用 `git stash -u`。
- 本次练习中的 `temp.txt` 在 stash 后仍显示为未跟踪文件，说明它没有被普通 `git stash` 保存；实际保存的是当时已被 Git 跟踪的文件修改。

## 3. 重点理解

### 文件类型、元数据和 inode

- `file` 主要回答“这个文件的内容属于什么类型”。
- `stat` 主要回答“这个文件在文件系统中具有什么属性”。
- 文件名是目录项中的名称，目录项把文件名关联到 inode。
- inode 保存文件的核心元数据，同一个 inode 可以通过多个硬链接文件名访问。
- `Unicode text, UTF-8 text` 表示文本包含 Unicode 字符并使用 UTF-8 编码，不表示它是二进制程序。

### 内核、发行版和架构

- Linux 严格来说是内核。
- Ubuntu 是基于 Linux 内核构建的完整发行版，包含系统工具、软件包管理、服务和可选桌面环境，不只是操作界面。
- `x86_64` 主机为 `aarch64` 目标构建程序时，通常需要对应的交叉编译工具链。

### 磁盘与内存

- `df` 的统计对象是文件系统，适合查看某个挂载点还剩多少空间。
- `du` 的统计对象是指定文件或目录，适合查看它实际占用多少磁盘空间。
- `free` 表示当前完全空闲的内存。
- `available` 还考虑系统可回收的缓存，更适合估计在不发生明显交换时还能提供给程序的内存。

### 平均负载

- `uptime` 的三个负载值依次对应过去 1、5、15 分钟。
- 负载统计处于可运行状态或不可中断睡眠状态的平均任务数，不是 CPU 百分比。
- 负载需要结合逻辑 CPU 数判断。例如负载 `4.0` 在 4 核系统上可能接近满载，在 16 核系统上通常仍有较多余量。

### Shell 状态和参数

- `$?` 只保存上一条命令的退出状态；执行新命令后会立即被覆盖，所以必须及时检查。
- `echo hello` 是有效的 Shell 内置命令，成功后会把 `$?` 改为 `0`。
- `${1:-day4_system_check.log}` 表示：第一个参数未设置或为空时使用默认日志名，否则使用第一个参数。
- `local command_name` 将变量限制在当前函数内，避免影响函数外的同名变量。
- `return 0` 或 `return 1` 结束当前函数，并向调用者返回成功或失败状态。
- `exit 1` 结束整个脚本，而不只是结束当前函数。
- `check_command "$command_name" || exit 1` 表示只有命令检查失败时，才以状态 `1` 终止脚本。
- `>&2` 把错误文字写入标准错误，便于将正常结果和错误信息分开处理。

## 4. 诊断脚本的执行流程

`day4_system_check.sh` 是一个最小系统诊断工具，流程如下：

1. 根据第一个参数决定日志名称；没有参数时使用默认名称。
2. 检查 `date`、`uname`、`hostname`、`df`、`free`、`uptime` 六个依赖命令。
3. 如果缺少依赖，向标准错误输出原因并以状态 `1` 结束，不生成不完整报告。
4. 如果依赖完整，收集主机、内核、架构、磁盘、内存和负载信息。
5. 将系统信息写入日志，并告诉用户日志保存位置。

## 5. 遇到的问题、根因与解决

### 脚本没有执行权限

- 现象：运行脚本时提示“权限不够”。
- 根因：脚本最初没有执行权限。
- 解决：使用 `chmod +x day4_system_check.sh` 添加执行权限。

### 相对路径使用错误

- 现象：在 `robot-system-learning/linux` 目录中再次使用 `robot-system-learning/linux/day4_system_check.sh`，提示文件不存在。
- 根因：相对路径从当前目录开始计算，重复写入了目录层级。
- 解决：已经位于脚本目录时直接使用 `./day4_system_check.sh`。

### 命令输入错误

- `at day4_custom.log` 应为 `cat day4_custom.log`。
- `;s` 不是有效命令，分号出现在没有前置命令的位置会产生语法错误。

### `echosss` 导致日志内出现错误

- 现象：日志中出现 `echosss: 未找到命令`，但脚本仍可能返回 `0`。
- 根因：`echosss` 在 Shell 语法上可以作为命令名，因此 `bash -n` 不会报语法错误；运行时才会发现命令不存在。后续的 `uptime` 成功又让命令组最终返回成功状态。
- 解决：将 `echosss` 修正为 `echo`，重新执行正常和异常验证。
- 经验：语法检查通过不等于运行逻辑正确，还必须检查日志、退出状态和产出文件。

## 3. 脚本整体逻辑

1. 读取搜索目录和关键字；没有参数时使用默认值。
2. 先判断搜索目录是否存在。
3. 使用 `find` 收集日志路径，并安全地保存到 Bash 数组。
4. 没有日志文件时直接返回状态 `3`。
5. 使用 `grep` 搜索全部日志并立即保存其退出状态。
6. 根据状态输出匹配成功、没有匹配或执行错误。

这里的重点是理解流程，不要求记忆 `mapfile`、`-print0` 等参数细节。使用空字符分隔路径并保存到数组，是为了避免文件名中的空格或换行被错误拆分。

## 4. 学习问题与解答

### 为什么 `find -exec grep` 的状态不能简单等同于匹配结果

- 使用 GNU `find -exec ... {} +` 时，如果找到了文件并执行 `grep`，`grep` 的非零结果可能使 `find` 最终也返回非零。
- 如果没有找到任何文件，`grep` 根本没有执行，而 `find` 仍可能返回 `0`。
- 所以只查看 `find` 的状态，无法可靠区分“找到关键字”和“没有文件可搜索”。脚本直接运行 `grep` 并保存它的状态，含义更明确。

### 为什么使用 `-print0` 和数组保存路径

- 普通空格或换行分隔可能把一个文件名拆成多个部分。
- 空字符不能出现在 Linux 文件名中，适合作为路径之间的可靠分隔符。
- 数组让每个日志路径作为一个独立参数传给 `grep`。

### `grep` 和脚本退出状态表示什么

- `grep` 返回 `0` 表示找到匹配，返回 `1` 表示没有匹配，大于 `1` 表示执行错误。
- 脚本返回 `0` 表示找到关键字，`1` 表示没有匹配行，`2` 表示目录不存在，`3` 表示没有日志文件。

### 为什么关键字前使用 `--`

- `--` 表示选项到此结束。
- 后面的 `-n` 等内容会被当作普通搜索文本，而不是命令选项。

### 为什么删除前必须使用相同条件预览

- 预览可以确认搜索起点、深度、文件类型和名称条件是否正确。
- 只有预览结果完全符合预期，才把最终动作从显示改为删除。

## 4. 学习问题与解答

### `grep` 在日志分析中的输入、处理和输出是什么

- 输入是一份日志文件或其他文本。
- 处理是根据指定条件筛选需要关注的行。
- 输出是匹配内容以及用于判断结果的证据。

### 为什么固定标签适合按字面量匹配

- `[ERROR]` 是一个完整、固定的日志标签。
- 普通正则会把方括号解释为特殊规则，只匹配其中任意一个字符，容易产生误匹配。
- 字面量匹配把整个标签当作普通文字，结果与需求一致。

### 正则表达式适合什么场景

- 当内容存在变化规律时适合使用正则，例如温度后面的数字。
- 当需要表达多个可能模式时也可使用正则，例如同时匹配 `ERROR` 或 `WARN`。
- 这部分只需知道用途，不要求用户记忆或独立编写正则。

### 上下文能提供什么证据

- 上下文显示故障前的状态和故障后的动作。
- 它能帮助建立事件顺序、缩小排查范围，但不能仅凭相邻几行确定根因。

### 为什么错误优先于警告

- 错误通常代表更严重的问题，需要优先处理。
- 同一日志同时包含错误和警告时，最终结果应先反映最高严重等级。
- 警告表示需要关注的异常或风险，不保证系统一定不受影响。

### 为什么分析脚本不修改日志

- 原始日志是定位和复现故障的证据。
- 分析过程中修改或删除日志会破坏证据，也会让后续复验失去可靠输入。
- 日志读取和日志清理应由不同工具负责。

## 5. 遇到的问题与纠正

### `[ERROR]` 出现误匹配

- 现象：原本只想找错误标签，普通搜索却显示全部五行。
- 原因：方括号在正则表达式中表示匹配其中任意一个字符。
- 解决：固定标签改用字面量匹配。
- 经验：匹配结果过多时，先检查搜索条件是否被当作正则解释。

### 对日志等级的理解过于绝对

- 原理解：警告不影响运行，错误表示系统一定无法执行。
- 纠正：警告表示存在需要关注的异常或风险；错误表示更严重的事件，但是否导致整个系统停止还需结合上下文判断。

# Day8 诊断管道与证据保存学习记录

## 1. 学习目标

- 理解标准输出和标准错误是两条不同的数据通道。
- 使用 `tee` 同时显示筛选结果并保存报告。
- 避免旧报告污染本次测试结论。
- 使用逐段检查定位管道中首次偏离预期的位置。
- 完成 `day8_diagnostic_pipeline.sh` 诊断管道工具。

## 2. 实际执行与结果

### 筛选与统计管道

- 混合日志包含五行记录。
- 筛选阶段得到一条警告和两条错误。
- 筛选结果进入统计阶段后得到三行，而不是统计原日志全部五行。
- 已理解管道左侧是上游，左侧输出成为右侧下游的输入。

### 标准输出与标准错误

- `[NORMAL] diagnostic output` 是标准输出，经过管道进入 `tee`。
- `tee` 将该内容显示在终端并写入 `stdout-only.txt`。
- `[ERROR STREAM] simulated failure` 使用标准错误，默认绕过管道直接显示在终端。
- 因此屏幕显示了两行，但报告文件只包含标准输出的一行。

### 使用 tee 保存证据

- 混合日志经过筛选后，屏幕和 `attention-report.txt` 都得到三行关注信息。
- 使用正常日志重新运行后，报告被覆盖为零行，旧的三行没有残留。
- 这证明报告是可重新生成的分析产物，每次测试应反映本次输入，而不是历史结果。

### 诊断脚本验证

- 混合日志显示三条关注信息，报告包含三行，结论为 `attention required`。
- 正常日志覆盖同一报告后，报告为零行，结论为 `no warning or error found`。
- 输入日志不存在时，脚本明确提示输入文件不存在，不输出虚假的分析结论。
- 脚本语法检查和独立复验均通过。

## 3. 诊断管道整体逻辑

`day8_diagnostic_pipeline.sh` 的处理流程如下：

1. 接收输入日志与报告文件路径。
2. 检查输入日志是否存在。
3. 从日志中筛选警告和错误。
4. 使用 `tee` 把筛选结果显示在屏幕并覆盖写入本次报告。
5. 统计报告中的关注行数。
6. 根据是否存在关注行显示最终结论。

学习重点是理解数据如何逐阶段传递，不要求记忆命令参数或数字状态码。

## 4. 学习问题与解答

### 管道中的上游和下游是什么

- 管道左侧命令是上游，右侧命令是下游。
- 上游的标准输出成为下游的标准输入。
- 下游处理的是上游给出的内容，不一定是原始文件的全部内容。

### 为什么屏幕错误不一定进入报告

- 管道默认只连接标准输出。
- 标准错误默认绕过管道并直接显示在终端。
- 因此“屏幕看见了错误”和“报告保存了错误”是两件不同的事。

### tee 解决什么问题

- `tee` 接收上游送来的标准输入。
- 它把同一份内容写入报告，同时继续输出到屏幕或下一阶段。
- `tee` 不会自动收集没有进入管道的标准错误。

### 为什么不能保留旧报告冒充新结果

- 旧报告对应的是历史输入和历史执行过程。
- 如果本次没有覆盖生成报告，旧内容可能被误认为当前故障证据。
- 报告必须和本次输入及本次执行一一对应。

### 为什么分析报告可以覆盖，原始日志不能修改

- 报告是根据原始日志生成的派生结果，可以重新生成。
- 原始日志是定位和复现问题的证据，修改后会丢失真实现场。
- 分析工具必须保持输入只读。

## 5. 遇到的问题与纠正

### 标准输出和标准错误方向混淆

- 初始理解把 `[NORMAL]` 误认为标准错误。
- 文件内容提供了直接证据：`stdout-only.txt` 保存了 `[NORMAL]`，说明它经过了管道和 `tee`。
- 最终确认：没有 `>&2` 的正常文字是标准输出；带 `>&2` 的模拟错误是标准错误。

### 对 tee 的作用理解错误

- 初始理解认为 `tee` 可以解决标准错误无法进入报告的问题。
- 纠正后确认：`tee` 只复制已经到达其标准输入的数据，不会自动改变上游的错误通道。

### 空报告的逐段排查

- 原始混合日志确实包含异常。
- 单独执行筛选阶段得到三行，说明输入和筛选阶段正常。
- `script-report.txt` 为空，是因为它此前被正常日志覆盖，之后没有用混合日志重新生成。
- 结论：空报告不是当前混合日志的有效分析结果；问题位于报告生成时序，而不是原始日志或筛选条件。

# Day12 用户、组与权限学习记录

## 1. 学习目标

- 能确认当前用户、主组和附加组。

- 理解系统根据当前身份选择一组权限，不会把三组权限相加。

- 能根据身份、路径、文件归属和权限证据排查访问失败。

## 2. 权限字符串重点结构

> **重点：权限字符串由“文件类型 + owner + group + other”组成。**

```text
- rw- --- ---
│  │   │   └─ other：既不是 owner、也不属于文件所属组的其他用户
│  │   └───── group：属于文件所属组的用户
│  └───────── owner：文件所有者
└──────────── 文件类型：“-”是普通文件，“d”是目录
```

### 每个符号的含义

- `r`：允许读取。
- `w`：允许写入。
- `x`：允许执行；对目录表示允许通过该目录访问路径中的对象。
- `-`：对应位置没有该项权限。
- `---`：这一类用户没有读、写、执行权限，不是拥有全部权限。

### 系统选择哪组权限

```text
当前用户是文件 owner？
├─ 是 → 只检查 owner 权限
└─ 否 → 当前用户所属组与文件 group 匹配？
         ├─ 是 → 只检查 group 权限
         └─ 否 → 只检查 other 权限
```

- owner、group、other 是三种身份分类，不是三组可以相加的权限。
- 当前用户即使属于多个组，只要他就是文件 owner，本次访问就使用 owner 权限。
- `group` 指文件自身记录的所属组，不是“owner 所属的所有组”。
- `other` 指剩余用户，不是“owner 所属的其他用户组”。

# Day13 chmod 与 chown 学习记录

## 1. 学习目标

- 区分 `chmod` 与 `chown` 修改的文件元数据。
- 通过变更前后的证据确认权限、owner 和 group 的变化范围。

## 2. 核心区别

| 命令 | 修改对象 | 不直接修改 |
|---|---|---|
| `chmod` | 文件权限 | owner、group、文件正文 |
| `chown` | owner、group，或同时修改两者 | 文件正文 |

- 权限、owner 和 group 都是文件元数据，不是文件正文。
- `chmod` 成功后要检查权限是否符合预期，同时确认 owner 和 group 未被意外改变。
- `chown` 成功后要检查 owner/group 是否符合预期，同时确认权限和内容未被意外改变。

变更前：-rw-r----- | owner=seeway | group=l
增加组写权限：-rw-rw---- | owner=seeway | group=l

# Day14 进程、PID、ps 与 top 学习记录

## 1. 学习目标

- 区分磁盘上的程序文件与运行中的进程实例。
- 理解 PID 和 PPID 的作用及父子进程关系。
- 使用 `ps` 获取进程快照，使用 `top` 观察目标进程和系统概要。

## 2. 核心概念

### 程序与进程

- 程序是存储在磁盘上的代码文件，没有运行时也可以存在。
- 进程是程序运行后产生的实例，具有 PID、PPID、运行用户、状态和资源。
- 进程结束后该运行实例消失，程序文件通常仍然存在。

### PID 与 PPID

- PID 标识当前正在运行的某个进程实例。
- PPID 表示启动该进程的父进程 PID。
- PID 在当前时刻可用于精确定位实例，但不是永久编号；进程结束后，该数字可能被系统重新使用。
- 因此旧 PID 不能永久充当进程仍在运行的证据，必须重新查询。

### ps 与 top

- `ps` 获取执行命令那个时刻的进程快照。
- `top` 正常交互使用时持续刷新系统和进程状态。
- Day14 使用 `top` 的单次批处理输出，方便在 `out.md` 保存证据。
- `htop` 未安装不影响进程观察，Day14 没有为了练习安装软件。

# Day15 kill、pkill 与 signal 学习记录

## 1. 学习目标

- 理解 signal 是发送给进程的通知，`kill` 的核心作用是发送信号。
- 理解 `TERM` 用于请求进程结束，目标进程可以在退出前执行清理。
- 在发送信号前确认目标，发送后重新查询结果。
- 区分 `kill` 按 PID 定位与 `pkill` 按名称或模式匹配。
- 使用 `process_check.sh` 检查指定 PID 是否正在运行或可访问。

## 2. 核心概念

### kill、TERM 与进程退出

- `kill` 并不等于无条件强制结束进程，它的核心动作是向目标进程发送信号。
- Day15 使用 `TERM` 请求临时 worker 正常结束，没有实践强制终止信号。
- 目标进程可以处理 `TERM`，先执行清理逻辑，再退出。
- 发送命令成功不能单独证明进程已经退出，必须重新查询目标状态。

### kill 与 pkill 的目标范围

- `kill` 根据 PID 定位一个明确的进程实例。
- `pkill` 根据进程名称或模式选择目标，一次可能匹配多个进程。
- `pkill` 不是固定意义上的模糊搜索；匹配范围取决于名称、模式和使用方式。
- 使用 `pkill` 前，应先用完全相同的精确模式查看匹配结果，确认不会影响无关进程。

### kill -0

- `kill -0` 不发送终止信号，只检查目标进程是否存在且当前用户是否可以访问。
- 检查成功表示目标存在并且当前用户有相应访问权限。
- 检查失败可能表示进程不存在，也可能表示当前用户无权访问，不能只解释为进程不存在。

# Day16 systemd、systemctl 与服务状态学习记录

## 1. 学习目标

- 理解 systemd、service unit、`systemctl` 和服务进程的整体关系。
- 区分 unit 的加载状态、当前运行状态和启用状态。
- 使用用户服务安全完成 `status`、`start` 和 `stop` 实验。

- 只读检查 SSH、CAN 相关服务，不修改真实系统服务。

## 2. 核心概念

### systemd、unit 与 systemctl

- systemd 是系统和服务管理器，负责读取 unit 配置并管理服务生命周期。
- service unit 是描述服务如何被启动和管理的配置，不是运行中的服务进程。
- `systemctl` 是向 systemd 发送查询或控制请求的命令行工具。
- unit 文件存在只表示配置存在，不能证明对应服务正在运行。

### 三类状态

- `LoadState` 回答 unit 配置是否被找到并加载。
- `ActiveState` 和 `SubState` 回答服务当前是否运行以及更具体的运行状态。
- `UnitFileState` 回答 unit 文件的安装或启用状态，例如 `enabled`、`disabled`、`static`、`masked` 或 `linked`。
- `start/stop` 改变当前运行状态；`enable/disable` 改变自动启动配置，两者不能混为一谈。

### 常见 UnitFileState

- `static`：不能独立 enable，通常由其他 unit 依赖或手动启动。
- `masked`：unit 被屏蔽，不能启动，比 disabled 限制更强。
- `generated`：unit 由 systemd 在启动或重载时动态生成。
- `alias`：该名称是另一个 unit 名称的别名。

## 2. 核心概念

### socket 与 ss

- socket 是应用程序使用网络协议栈通信的端点，包含协议、本地地址、端口和状态等信息。
- `ss` 从内核读取并显示查询时刻存在的 socket 状态，不会因为查询而创建或关闭 socket。
- socket 存在只证明程序绑定或监听了端口，不证明应用能够正确处理请求或返回业务结果。
- Day19 的 ping 证明 ICMP 往返，Day20 的 ss 增加本机传输层 socket 证据，两者都不能替代应用功能验证。

### TCP 与 UDP

- TCP 通信前需要建立连接，按顺序传输字节流；等待连接的监听 socket 通常显示 `LISTEN`。
- UDP 不建立 TCP 式连接，直接收发数据报；绑定后的 socket 通常显示 `UNCONN`。
- TCP 和 UDP 使用不同的协议空间，相同端口数字可以分别对应不同 socket。
- 查询端口时必须同时确认协议，不能仅凭端口数字判断目标 socket。

# Day22 USB 识别与 lsusb 学习记录

## 1. 学习目标

- 读懂 `lsusb` 的 Bus、Device、`VID:PID` 和设备描述。

- 区分设备已枚举、驱动已绑定、权限可用和应用功能正常。

## 2. 核心概念

### USB 枚举与身份字段

- USB 枚举表示主机发现设备并读取到基本描述信息。
- `lsusb` 展示查询时已经枚举的 USB 设备；它不会证明应用已经能够正常使用设备。
- Bus 是当前 USB 总线号，Device 是该总线上的当前设备号，两者可能随重新连接发生变化。
- `VID` 是厂商 ID，`PID` 是产品 ID；`VID:PID` 通常标识产品型号，不是每台物理设备的唯一编号。
- 设备描述来自 usbutils 使用的 ID 数据，可能完整、简略或缺失。

### 列表与拓扑

- `lsusb` 默认列表侧重设备身份和 `VID:PID`。
- `lsusb -t` 侧重设备连接层级、接口类别、已绑定驱动和连接速率。
- 树形输出出现驱动，只能增加驱动绑定证据，仍不能替代权限和应用通信验证。

## 3. 实际执行与结果

### 工具与真实枚举

- `lsusb` 位于 `/usr/bin/lsusb`，版本为 usbutils `014`。
- 真实枚举成功，状态为 `0`；结果包含两个 Linux Foundation root hub、一个 Logitech 接收器和一个 Genesys Logic Hub。
- 选中的真实设备为 `Bus 001 Device 002: ID 046d:c534 Logitech, Inc. Unifying Receiver`。
- `046d` 是 Logitech 的厂商 ID，`c534` 是该接收器的产品 ID。
- Logitech Unifying Receiver 是兼容无线键盘或鼠标使用的 USB 接收器；该描述不能单独说明当前具体配对了哪个外设。

### USB 树形信息

- `lsusb -t` 成功，状态为 `0`。
- Bus 02 的 root hub 使用 `xhci_hcd/4p`，输出速率为 `20000M/x2`。
- Logitech 接收器对应 Dev 2，提供两个 Human Interface Device 接口，均由 `usbhid` 驱动，输出速率为 `12M`。
- Genesys Logic Hub 对应 Dev 3，类别为 Hub，驱动为 `hub/4p`，输出速率为 `480M`。

### VID:PID 过滤

- 使用真实 `VID:PID` 过滤取得对应设备，状态为 `0`。
- 使用合法但未匹配的 `0000:0000` 时没有输出，状态为 `1`。
- 使用格式错误的 `not-an-id` 时显示用法信息，状态为 `1`。
- 没有匹配表示当前枚举列表找不到指定 ID；格式错误表示输入尚未被解析为合法 ID。

### usb_device_check.sh

- 新增 `robot-system-learning/linux/usb_device_check.sh`。
- 脚本先检查空输入和 `VID:PID` 格式，再执行 `lsusb`，最后查找匹配行。
- 空输入和格式错误返回 `1`；枚举环境失败返回 `2`；枚举成功但无匹配返回 `1`；找到设备返回 `0`。
- 脚本通过 `bash -n` 语法检查，权限为 `744`，owner 具有执行权限。
- 使用 `046d:c534` 时找到 Logitech 接收器并返回 `0`；使用 `0000:0000` 时返回无匹配错误和状态 `1`。

## 4. 遇到的问题与纠正

### Shell 变量赋值不能在等号两侧留空格

- 第一次执行 `usb_id = '1d6b:0003'` 时，Shell 把 `usb_id` 当成命令，因此提示未找到命令。
- 正确赋值为 `usb_id='1d6b:0003'`；本次已用正确写法完成后续验证。

### 漏写引号导致续行提示

- 第一次输出正常分支状态时，`printf` 的最后一个双引号缺失，Shell 显示 `>` 等待命令继续输入，随后使用 `Ctrl+C` 中断。
- 该错误发生在脚本已经找到设备之后，但当次状态记录不完整。
- 复查时重新执行完整命令，取得 Logitech 接收器输出和可信的 `found_status=0`。

### 实机输出误写为样例

- 本机 `lsusb` 已成功枚举，不需要使用受限环境的教学样例。
- 记录中的“样例 Bus”等字段实际来自本机输出，标题使用不准确；原始学习过程保留，归档按真实枚举结果说明。

### 枚举证据边界

- 初次回答把 `lsusb` 找到设备说成只证明工具存在，这不正确。
- 纠正：找到设备证明本次 USB 枚举成功，但不能证明驱动、当前用户权限和应用通信都正常。
- 技术回答中的“16禁止”是文字错误，正确表述是“十六进制 `VID:PID` 格式”。
