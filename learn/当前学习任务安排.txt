Day14 详细学习安排：进程、PID、ps 与 top

- 理解 PID 用于标识一个正在运行的进程，PPID 表示启动它的父进程。
- 能用 `ps` 获取某一时刻的进程快照。
- 能用 `top` 观察系统和目标进程的动态状态。

二、认识当前 Shell 进程

任务 1：查看当前 Shell 的 PID 和进程信息

执行：

```bash
printf 'current shell PID: %s\n' "$$"
ps -p "$$" -o pid,ppid,user,stat,etime,cmd
```

重点观察：

- 第一条输出当前 Shell 的 PID。
- `ps` 中的 PID 应与 `$$` 输出一致。
- PPID 是启动当前 Shell 的父进程 PID。
- USER 是运行该进程的用户。
- STAT 表示当前状态，ETIME 表示进程已经运行多久，CMD 表示启动命令。

整体逻辑：

```text
终端或上级程序
       ↓ 启动
当前 Shell 进程
       ↓
获得自己的 PID，并记录父进程 PPID
```

重点理解：

- PID 标识的是一次运行实例，不是磁盘文件的永久编号。
- 同一个程序多次运行时，每个进程会有各自的 PID。
- 不要求记住输出列参数，只需能从结果中找到 PID、PPID 和命令。

验证标准：

- 保留 `$$` 和 `ps` 的真实输出。
- 两处 Shell PID 一致。

三、查看系统进程快照

任务 2：用 ps 获取当前时刻的进程证据

执行：

```bash
ps -eo pid,ppid,user,stat,etime,comm --sort=pid | head -n 15
```

重点理解：

- `ps` 输出是执行命令那个时刻的快照。
- 进程可能在下一刻启动、结束或改变状态，因此旧快照不能永久代表当前系统。
- 一行通常代表一个进程实例，不同 PID 表示不同运行实例。

验证标准：

- 保留前15行真实输出。
- 能指出其中任意一行的 PID、PPID、USER 和命令名。

四、临时诊断 worker 生命周期实验

任务 3：启动、观察并等待一个临时后台进程自然结束

请将下面整段命令一次执行：

```bash
shell_pid="$$"

bash -c 'exec -a robot-system-diagnostic-worker sleep 8' &
worker_pid="$!"

printf 'shell PID: %s\n' "$shell_pid"
printf 'worker PID: %s\n' "$worker_pid"

printf '%s\n' '[PS] exact worker snapshot'
ps -p "$worker_pid" -o pid,ppid,user,stat,etime,cmd

printf '%s\n' '[PS] children of current shell'
ps --ppid "$shell_pid" -o pid,ppid,user,stat,etime,cmd

printf '%s\n' '[SEARCH] worker by name'
pgrep -af 'robot-system-diagnostic-worker'

printf '%s\n' '[TOP] worker snapshot'
top -b -n 1 -p "$worker_pid" | head -n 12

wait "$worker_pid"

printf '%s\n' '[PS] after worker finished'
ps -p "$worker_pid" -o pid,ppid,user,stat,etime,cmd ||
  printf '%s\n' '[EXPECTED] worker is no longer running'
```

预期：

- `worker_pid` 是后台 worker 的 PID。
- worker 的 PPID 与 `shell_pid` 一致，证明当前 Shell 启动了它。
- `ps`、名称搜索和 `top` 都能在 worker 存活期间找到它。
- worker 命令行包含 `robot-system-diagnostic-worker`。
- `wait` 只等待 worker 自然结束，没有发送终止信号。
- 最后再次查询该 PID 时，显示预期的“不再运行”结果。

生命周期：

```text
当前 Shell
    ↓ 启动
临时 worker 获得 PID
    ↓
ps / top 获取运行证据
    ↓
8秒后自然结束
    ↓
原 PID 不再对应该 worker
```

重点理解：

- `$!` 提供当前 Shell 最近启动的后台进程 PID；不要求记忆写法，只需理解本次如何得到精确目标。
- 后台运行表示 Shell 可以在 worker 存活期间继续执行观察命令。
- PID 只在进程存在期间用于定位该实例；进程结束后不能继续把旧 PID 当成有效运行证据。
- 不要求理解 `exec -a` 细节，它只为临时 worker 设置便于搜索的名称。

验证标准：

- 保留 worker PID、PPID、`ps`、名称搜索和 `top` 输出。
- 保留 worker 自然结束后的查询结果。
- 根据输出确认 worker 的父进程是当前 Shell。

五、理解 ps 与 top 的证据差异

任务 4：根据刚才的实际输出比较两种观察方式

`ps` 的整体作用：

- 获取执行时刻的进程快照。
- 适合记录明确的 PID、PPID、用户、状态、运行时间和命令。
- 再次执行才会得到新的当前状态。

`top` 的整体作用：

- 正常交互使用时会持续刷新系统和进程状态。
- 本次使用批处理单次输出，便于把结果记录到 `out.md`。
- 输出同时包含系统负载、CPU、内存概要和目标进程信息。

验证标准：

- 能根据实际输出指出两者都找到了同一个 worker PID。
- 理解 `ps` 是快照，`top` 通常用于持续观察；不要求记住操作按键。

七、检查当前 ROS2 相关进程

任务 6：在系统进程快照中查找可识别的 ROS2 相关命令

执行：

```bash
ps -eo pid,ppid,user,stat,etime,cmd |
  grep -E '[r]os2|[r]obot_state_publisher' ||
  printf '%s\n' '[INFO] no matching ROS2-related process is currently visible'
```

结果判断：

- 有输出时：记录匹配进程的 PID、PPID、用户和命令。
- 无输出时：如实保留提示，表示本次快照没有发现名称匹配的进程。
- 名称没有匹配不等于 ROS2 软件没有安装，也不能证明系统永远没有 ROS2 节点；它只说明本次搜索没有取得匹配证据。

重点理解：

- 只有正在运行的程序才会出现在进程列表中。
- 磁盘上存在程序文件，不代表它当前一定有对应进程。
- 以后实际启动 ROS2 节点时，可以根据启动命令、已知进程名或 PID 使用同样方法观察。

验证标准：

- 保留真实匹配结果或无匹配提示。
- 不编造不存在的 ROS2 节点或 PID。

八、进程问题的基础诊断顺序

任务 7：形成进程层面的取证流程

当预期的程序似乎没有运行时，按下面顺序思考：

1. 明确预期运行的程序或命令名称。
2. 用进程快照搜索匹配对象。
3. 有结果时记录 PID、PPID、USER、STAT、ETIME 和 CMD。
4. 无结果时区分“进程已经结束”和“搜索名称不准确”，不能直接认定程序未安装。
5. 对已知 PID 再做精确查询，确认该实例当前是否仍存在。
6. 需要持续观察时使用动态工具，重新获取当前证据。

说明：

- Day14 只负责识别和观察进程。
- 不对系统服务或不熟悉的进程执行任何修改或终止操作。

验证标准：

- 能按目标、搜索、确认身份、观察状态、重新验证的顺序说明过程。
