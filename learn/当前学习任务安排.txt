二、理解 journald 与 journalctl

任务 1：建立整体概念

```text
服务和系统组件产生日志事件
             ↓
systemd-journald 收集到 journal
             ↓
journalctl 按 unit、时间等条件查询
             ↓
终端输出或项目日志报告
```

重点理解：

- systemd-journald 是日志收集服务，`journalctl` 是读取和筛选 journal 的查询工具。
- `journalctl` 默认只读，不会因为查询而修改原始 journal。
- unit 名称和时间范围是查询输入，匹配日志或错误文字是输出。
- Day16 的 `status` 关注当前服务状态；Day17 的 journal 记录服务在一段时间内发生的事件。
- 没有查询结果只表示当前条件下没有取得日志，不能单独证明服务不存在或一直正常。

验证标准：

- 后续能把日志产生、journald 收集、journalctl 查询和报告输出连成完整流程。

五、使用 -u 与 --since 查询本次事件

任务 4：生成并查询明确时间范围内的日志

执行：

```bash
start_marker="$(date '+%Y-%m-%d %H:%M:%S')"
printf 'start marker: %s\n' "$start_marker"

systemctl --user start day16-practice.service
sleep 1
systemctl --user stop day16-practice.service

journalctl --user -u day16-practice.service \
  --since "$start_marker" --no-pager
```

预期：

- 输出只查询 `start_marker` 之后与 `day16-practice.service` 相关的用户日志。
- 日志中应出现练习服务启动和停止相关事件。
- 日志时间不早于记录的 start marker。

重点理解：

- `-u` 把查询范围限制到指定 unit。
- `--since` 把查询范围限制到指定时间之后。
- 两个条件组合后，可以减少无关历史日志。
- 记录时间标记必须发生在实验事件之前，才能覆盖完整过程。

验证标准：

- 保留 start marker、服务启停命令和对应日志输出。

六、使用 -f 观察新增日志

任务 5：用自动超时方式观察新事件

请将下面整段命令一次执行：

```bash
follow_output='/tmp/day17-journal-follow.out'
follow_marker="$(date '+%Y-%m-%d %H:%M:%S')"

: > "$follow_output"

timeout 8s journalctl --user -f -u day16-practice.service \
  --since "$follow_marker" --no-pager > "$follow_output" 2>&1 &
follow_pid="$!"

sleep 1
systemctl --user start day16-practice.service
sleep 1
systemctl --user stop day16-practice.service

wait "$follow_pid" 2>/dev/null || true

cat "$follow_output"
```

预期：

- `-f` 在运行期间等待新的匹配日志。
- 启动和停止练习服务后，`follow_output` 中出现对应的新事件。
- `timeout` 在8秒后结束观察，最终没有残留 follow 进程。

回归检查：

```bash
ps -p "$follow_pid" -o pid,ppid,user,stat,etime,cmd ||
  printf '%s\n' '[EXPECTED] journal follow process has ended'
```

验证标准：

- 保留实时观察取得的新日志和 follow 进程结束证据。
- `/tmp/day17-journal-follow.out` 不提交到 Git。

八、创建日志收集脚本

任务 7：为 Robot System Diagnostic Tool 创建项目脚本

执行：

```bash
vim service_log_collect.sh
```

在 Vim 中写入下面的完整内容：

```bash
#!/bin/bash

unit_name="$1"
since_time="$2"
output_file="$3"

if [[ -z "$unit_name" || -z "$since_time" || -z "$output_file" ]]; then
    printf '%s\n' '[LOG COLLECTION ERROR] unit, since time and output file are required' >&2
    exit 1
fi

{
    printf '[LOG COLLECTION] unit=%s since=%s\n' "$unit_name" "$since_time"
    journalctl --user -u "$unit_name" --since "$since_time" --no-pager
} > "$output_file" 2>&1

collect_status="$?"

if (( collect_status != 0 )); then
    printf '[LOG COLLECTION ERROR] failed; report=%s\n' "$output_file" >&2
    exit "$collect_status"
fi

printf '[LOG COLLECTION COMPLETE] report=%s\n' "$output_file"
```

保存后执行：

```bash
bash -n service_log_collect.sh
chmod u+x service_log_collect.sh
ls -l service_log_collect.sh
cat service_log_collect.sh
```

脚本整体逻辑：

1. 接收 unit 名称、起始时间和输出文件三个输入。
2. 缺少输入时输出错误并停止。
3. 使用 journalctl 查询指定用户 unit 和时间范围。
4. 将查询条件、日志或 journalctl 错误保存到报告。
5. 查询成功时输出报告路径，失败时输出明确错误。

说明：

- 不要求记住脚本代码和参数，只需理解输入、查询、报告和错误的整体流程。
- 脚本提交到 Git，脚本生成的日志报告不提交。

验证标准：

- 脚本语法通过并具有 owner 执行权限。
- 文件位于 `robot-system-learning/linux/service_log_collect.sh`。

十二、日志问题的基础诊断顺序

任务 11：形成 journal 查询流程

```text
确认目标 unit 和管理范围（系统级或 --user）
                     ↓
确认本次问题发生的时间范围
                     ↓
使用 -u 与 --since 缩小查询范围
                     ↓
查看匹配日志或原始错误文字
                     ↓
需要观察新事件时使用限时 -f
                     ↓
修正输入或问题后重新查询验证
```

重点理解：

- 先确认对象和时间，再读取日志，避免被大量无关记录干扰。
- 日志是诊断证据，不应修改原始 journal。
- 查询无结果、查询参数错误和服务没有运行是不同情况。

验证标准：

- 能按 unit、管理范围、时间、日志结果和回归查询说明整体流程。
