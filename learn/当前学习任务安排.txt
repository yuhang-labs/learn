Day8 详细学习安排：诊断管道与证据保存

一、今日目标

- 把管道理解为“上一阶段输出成为下一阶段输入”的数据链路。
- 理解管道默认传递标准输出，标准错误不会自动进入下一阶段。
- 使用 `tee` 在屏幕显示结果的同时保存证据文件。
- 学会管道结果异常时逐段检查，而不是直接猜测最终命令有问题。
- 完成并验证 `day8_diagnostic_pipeline.sh` 诊断信息提取工具。
- 保证输入日志只读，并避免旧报告污染本次测试结果。

说明：

- Day2、Day3 已学习基础管道用法，今天不重复“管道符是什么”的简单练习。
- Day8 原手册主题是“管道”，今天重点学习数据流、标准错误边界、证据保存和逐段排查。

- 按用户要求，不考数字状态码、正则表达式细节，也不要求每日总结。
- 今天只学习 Linux 与 Shell，不新增 C++、CAN、ROS2 内容。

二、准备固定日志

任务 1：在 `/tmp` 中创建正常与异常日志

执行：

```bash
practice_dir='/tmp/day8-pipeline-practice'
mkdir -p "$practice_dir"

printf '%s\n' \
    '[INFO] robot boot' \
    '[WARN] motor temperature high' \
    '[INFO] retry motor' \
    '[ERROR] motor timeout' \
    '[ERROR] CAN offline' \
    > "$practice_dir/mixed.log"

printf '%s\n' \
    '[INFO] robot boot' \
    '[INFO] motor ready' \
    '[INFO] system healthy' \
    > "$practice_dir/clean.log"

wc -l "$practice_dir/mixed.log" "$practice_dir/clean.log"
```

预期：`mixed.log` 为 5 行，`clean.log` 为 3 行。

重点理解：

- `mixed.log` 包含一条警告和两条错误。
- `clean.log` 只包含正常信息。
- 测试数据位于 `/tmp`，不作为项目源码提交。

验证标准：

- 两份日志行数正确。
- 能说明两份日志分别用于验证什么场景。

三、把管道当作数据处理链

任务 2：观察“输入、筛选、统计”三个阶段

先只执行筛选阶段：

```bash
grep -F -e '[ERROR]' -e '[WARN]' "$practice_dir/mixed.log"
```

再执行完整管道：

```bash
grep -F -e '[ERROR]' -e '[WARN]' "$practice_dir/mixed.log" | wc -l
```

预期：

- 第一条命令显示一条警告和两条错误。
- 第二条命令输出 `3`，因为筛选结果包含三行。

整体理解：

```text
mixed.log → grep 筛选关注行 → wc 统计筛选后的行数
```

验证标准：

- 能指出每个阶段接收什么、输出什么。
- 能说明 `wc` 统计的是筛选后的内容，而不是原日志全部五行。
- 不要求记忆 `grep` 参数。

四、理解标准错误不会自动进入管道

任务 3：分别产生正常输出和错误输出

执行：

```bash
{
    printf '%s\n' '[NORMAL] diagnostic output'
    printf '%s\n' '[ERROR STREAM] simulated failure' >&2
} | tee "$practice_dir/stdout-only.txt"

cat "$practice_dir/stdout-only.txt"
```

预期：

- 终端可能同时看到正常文字和错误文字。
- `stdout-only.txt` 只保存 `[NORMAL] diagnostic output`。
- `[ERROR STREAM] simulated failure` 没有通过默认管道交给 `tee`。

重点理解：

- 管道默认连接前一个命令的标准输出与后一个命令的标准输入。
- 标准错误是另一条通道，默认直接显示在终端。
- 屏幕上看到了错误，不代表错误内容已经被下游工具或报告文件保存。
- 今天只理解这个边界，不要求记忆合并输出的写法。

验证标准：

- 能说明为什么屏幕出现两行，而文件只有一行。
- 能意识到检查报告文件时不能假设所有屏幕内容都在文件中。

五、使用 tee 同时显示并保存证据

任务 4：提取并保存关注行

执行：

```bash
grep -F -e '[ERROR]' -e '[WARN]' "$practice_dir/mixed.log" \
    | tee "$practice_dir/attention-report.txt"

cat "$practice_dir/attention-report.txt"
wc -l "$practice_dir/attention-report.txt"
```

预期：

- 屏幕显示三条关注信息。
- `attention-report.txt` 保存相同三行。
- 行数为 `3`。

继续使用正常日志覆盖生成报告：

```bash
grep -F -e '[ERROR]' -e '[WARN]' "$practice_dir/clean.log" \
    | tee "$practice_dir/attention-report.txt"

wc -l "$practice_dir/attention-report.txt"
```

预期：报告行数变为 `0`，旧的三行内容不应残留。

重点理解：

- `tee` 把收到的内容写入文件，同时继续输出到下一位置或屏幕。
- 每次验证应生成本次报告，不能让旧结果冒充新结果。
- 输入日志保持不变，报告文件是可重新生成的分析产物。

验证标准：

- 混合日志生成三行报告。
- 正常日志重新生成空报告。
- 能说明旧报告残留为什么会导致错误判断。

六、项目实践：诊断管道工具

任务 5：创建 `day8_diagnostic_pipeline.sh`

文件位置：

```text
robot-system-learning/linux/day8_diagnostic_pipeline.sh
```

完整代码：

```bash
#!/bin/bash

input_log="${1:-}"
report_file="${2:-/tmp/day8-attention-report.txt}"

if [ -z "$input_log" ] || [ ! -f "$input_log" ]; then
    echo "[PIPELINE ERROR] input log not found: $input_log" >&2
    exit 1
fi

echo "Input log: $input_log"
echo "Report file: $report_file"
echo "--- Attention lines ---"

grep -F -e '[ERROR]' -e '[WARN]' "$input_log" \
    | tee "$report_file"

matched_lines=$(wc -l < "$report_file")
echo "Matched lines: $matched_lines"

if [ "$matched_lines" -eq 0 ]; then
    echo "[RESULT] no warning or error found"
else
    echo "[RESULT] attention required"
fi
```

整体流程：

1. 接收输入日志和报告文件路径。
2. 先确认输入日志存在。
3. 筛选警告与错误信息。
4. 使用 `tee` 同时显示并覆盖生成本次报告。
5. 根据报告行数显示“无需关注”或“需要关注”。

要求：

- AI 已提供完整代码，用户只需创建文件、运行并理解数据流。
- 不要求学习脚本参数细节或数字状态码。
- 脚本只读取输入日志，报告保存到 `/tmp`，不提交报告文件。

任务 7：练习逐段排查

假设最终报告为空，但你认为日志应该包含错误，按下面顺序检查：

```bash
cat /tmp/day8-pipeline-practice/mixed.log

grep -F -e '[ERROR]' -e '[WARN]' \
    /tmp/day8-pipeline-practice/mixed.log

cat /tmp/day8-pipeline-practice/script-report.txt
```

重点理解：

1. 先确认上游输入是否真的包含预期内容。
2. 再单独运行中间筛选阶段。
3. 最后检查报告阶段。
4. 哪一阶段首次与预期不同，问题就更可能位于该阶段或它的输入。

验证标准：

- 三个脚本场景的屏幕输出和报告内容符合预期。
- 能说出逐段排查的先后顺序。
- 不要求检查或解释数字状态码。
- 运行脚本前后两份输入日志内容保持不变。
