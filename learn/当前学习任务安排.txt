Day13 详细学习安排：chmod 与 chown

一、今日目标

- 理解 `chmod` 修改权限，`chown` 修改文件的 owner 或 group。
- 能通过变更前后的 `stat` 输出判断究竟是哪项元数据发生变化。
- 理解文件 owner 通常可以修改自己的文件权限。
- 理解普通用户只能在有限范围内改变文件所属组，不能随意改变文件 owner 或改成自己不属于的组。
- 使用当前用户已经所属的 `adm` 组完成一次合法的 group 变更。
- 使用当前用户不属于的 `root` 组安全复现一次 `chown` 失败，并确认失败后元数据没有被错误改变。
- 验证 `chmod/chown` 修改的是文件元数据，不会修改文件内容。

说明：

- Day13 严格保持原学习计划的 `chmod/chown` 主题。
- Day2 已练习数字形式的 `chmod 755/644`，Day12 已练习符号形式的权限增减并掌握 owner/group/other。今天不重复权限数字换算和三组权限结构。
- Day13 的新增重点是区分 `chmod` 与 `chown` 的职责，以及普通用户执行 `chown` 的权限边界。
- 所有修改都作用于 `/tmp` 中的项目文件副本，不修改仓库中的 `robot_env.sh`。
- 不使用 `sudo`，不创建用户或组，不修改系统文件。
- AI 已提供全部命令，用户只需亲自在终端执行并理解整体变化。
- 不要求背命令参数、数字权限或错误状态码。
- 不要求填写每日总结。


预期：

- 项目原文件与临时副本内容相同，但它们是两个不同路径下的文件。
- 临时副本由当前用户拥有，初始 group 为 `l`，权限为 `-rw-r-----`。

重点理解：

- 今天把真实项目配置复制到 `/tmp`，后续只修改副本的元数据。
- `chmod` 在这里仅用于建立明确的初始状态，不重复学习权限数字。
- 项目原文件是对照对象，整个实验都不修改它。

验证标准：

- 确认 `test_file` 路径位于 `/tmp/day13-ownership-practice`。

三、验证 chmod 只修改权限

任务 2：只给副本的 group 增加写权限

变更前再次记录：

```bash
stat -c 'before chmod: permissions=%A | owner=%U | group=%G' "$test_file"
```

执行权限变更：

```bash
chmod g+w "$test_file"
stat -c 'after chmod:  permissions=%A | owner=%U | group=%G' "$test_file"
```

预期：

- 权限从 `-rw-r-----` 变为 `-rw-rw----`。
- owner 仍为 `seeway`。
- group 仍为 `l`。

整体逻辑：

```text
chmod 接收文件和目标权限
          ↓
修改权限位
          ↓
owner、group 和文件内容保持不变
```

随后恢复初始权限：

```bash
chmod g-w "$test_file"
stat -c 'restored: permissions=%A | owner=%U | group=%G' "$test_file"
```

验证标准：

- 保留变更前、变更后和恢复后的 `stat` 输出。
- 根据证据确认 `chmod` 只改变权限，没有改变 owner 或 group。

四、确认允许使用的测试组

任务 3：在执行 chown 前先确认当前用户属于 `adm`

执行：

```bash
groups
id -nG | tr ' ' '\n' | grep -Fx 'adm'
```

预期：

- `groups` 输出包含 `adm`。
- 第二条命令单独输出 `adm`。

重点理解：

- 文件 owner 可以把文件 group 改成自己所属的组。
- 先用身份和组证据确认变更条件，再执行 `chown`，不要盲目尝试。
- 今天只改变 group，不尝试把文件 owner 改成其他用户。

验证标准：

- 保留当前用户属于 `adm` 的真实证据。

五、验证 chown 修改所属组

任务 4：使用 chown 将副本的 group 从 `l` 改为 `adm`

执行：

```bash
stat -c 'before chown: permissions=%A | owner=%U | group=%G' "$test_file"

chown :adm "$test_file"

stat -c 'after chown:  permissions=%A | owner=%U | group=%G' "$test_file"
```

预期：

- group 从 `l` 变为 `adm`。
- owner 仍为 `seeway`。
- 权限仍为 `-rw-r-----`。

整体逻辑：

```text
当前用户是文件 owner，并且属于 adm 组
                    ↓
chown 只请求把文件 group 改为 adm
                    ↓
系统允许变更
                    ↓
group 改变，owner 和权限保持不变
```

重点理解：

- `chown` 可以修改 owner，也可以只修改 group；本次只使用它修改 group。
- 不要求记住 `:adm` 的具体写法，只需理解这次输入指定了目标 group。
- 当前用户仍然是文件 owner，因此后续访问仍优先使用 owner 权限，不会因为 group 改成 `adm` 就改用 group 权限。

验证标准：

- 保留变更前后的 `stat` 输出。
- 根据输出确认只有 group 发生变化。

六、安全复现 chown 失败

任务 5：尝试把副本改为当前用户不属于的 `root` 组

先确认当前用户不属于 `root` 组：

```bash
id -nG | tr ' ' '\n' | grep -Fx 'root' || printf '%s\n' '[EXPECTED] current user is not in group root'
```

随后执行预期失败的变更：

```bash
chown :root "$test_file"
stat -c 'after failed chown: permissions=%A | owner=%U | group=%G' "$test_file"
```

预期：

- 第一组命令确认当前用户不属于 `root`。
- `chown :root` 提示“操作不允许”或 `Operation not permitted`。
- 失败后 owner 仍为 `seeway`，group 仍为 `adm`，权限仍为 `-rw-r-----`。

调试逻辑：

1. 读取错误文字，确认是权限边界问题。
2. 用 `id` 或 `groups` 检查当前用户是否属于目标组。
3. 用 `stat` 检查失败后文件元数据是否保持原状。
4. 只对允许的目标组做恢复，不使用更高权限绕过实验。

重点理解：

- 普通用户不能任意决定文件 owner 或 group。
- 命令失败后不能只看错误，还要检查文件当前状态，确认没有发生部分变更。
- 今天不要求了解 Linux capability 或内核检查细节。

验证标准：

- 保留预期错误文字。
- 保留失败后的 `stat` 输出，确认 group 没有变成 `root`。

七、恢复所属组并验证文件内容

任务 6：将副本 group 恢复为主组 `l`，并证明文件内容未改变

执行：

```bash
chown :l "$test_file"
stat -c 'final: permissions=%A | owner=%U | group=%G' "$test_file"

cmp -s "$source_file" "$test_file" && printf '%s\n' '[OK] file content unchanged'
```

预期：

- 副本的 group 恢复为 `l`。
- owner 仍为 `seeway`，权限为 `-rw-r-----`。
- 内容比较显示 `[OK] file content unchanged`。

整体逻辑：

```text
chmod → 修改权限元数据
chown → 修改 owner/group 元数据
cmp   → 验证文件内容仍与项目原文件相同
```

重点理解：

- 权限和归属属于文件元数据，不是文件正文。
- `chmod/chown` 成功不代表文件内容被重新写入。
- 最终同时检查权限、owner、group 和内容，才构成完整回归验证。

验证标准：

- group 已恢复为 `l`。
- 项目原文件和临时副本内容仍然相同。
