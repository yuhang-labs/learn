- 理解 `/dev` 是 Linux 向用户空间提供设备访问入口的目录。

- 能使用 `ls`、`stat` 和 `file` 只读检查安全设备节点。
- 理解 `/dev/null`、`/dev/zero` 和 `/dev/full` 的不同读写行为。

二、理解应用、设备节点与内核设备的关系

任务 1：建立整体概念

```text
应用程序打开 /dev 下的设备节点
                ↓
内核根据设备节点找到对应的设备接口
                ↓
读写请求由设备本身的规则处理
                ↓
成功结果或具体错误返回给应用程序
```

重点理解：

- `/dev` 下的设备节点是应用访问设备的文件系统入口，不是设备硬件本身。
- 设备节点也不是驱动程序；驱动和内核负责处理应用对节点的操作。
- 字符设备按字符或字节流方式提供数据，例如今天使用的三个标准伪设备。
- 块设备按数据块访问，常用于存储设备；今天只理解概念，不查看或操作真实块设备。
- `ls -l` 第一列开头的 `c` 表示字符设备，`b` 表示块设备，`-` 表示普通文件。
- 权限决定当前用户能否尝试读写，但操作最终结果还取决于设备自身行为。

验证标准：

- 后续能按“应用 → 设备节点 → 内核设备接口 → 操作结果”的顺序解释实验。

三、检查安全设备节点的类型

任务 2：查看三个标准伪设备

执行：

```bash
ls -l -- /dev/null /dev/zero /dev/full

stat -c '%n type=%F permissions=%A' \
  /dev/null /dev/zero /dev/full

file -- /dev/null /dev/zero /dev/full
```

预期：

- `ls -l` 的类型字符均为 `c`。
- `stat` 将三个对象识别为字符特殊文件。
- `file` 将三个对象识别为 character special。
- 输出会显示权限以及主、次设备号，但本日不要求记忆数字。

重点理解：

- 三种工具从不同角度证明这些路径不是普通文件，而是字符设备节点。
- 节点类型与节点具体行为是两回事，后续需要通过受限实验分别验证。

验证标准：

- 保留三组完整输出，并能指出字符设备类型证据。

四、验证 /dev/null 的行为

任务 3：安全写入并读取 `/dev/null`

执行：

```bash
printf '%s\n' 'day21 discarded data' > /dev/null
null_write_status="$?"
printf 'null write status=%s\n' "$null_write_status"

wc -c < /dev/null
```

预期：

- 写入没有错误，`null_write_status=0`。
- 从 `/dev/null` 读取时立即结束，`wc -c` 输出 `0`。

重点理解：

- `/dev/null` 会丢弃写入的数据。
- 从 `/dev/null` 读取不会返回原先写入的内容，而是立即得到文件结束。
- 设备节点的行为不同于保存内容的普通文件。

验证标准：

- 保留写入状态和读取字节数 `0`。

五、验证 /dev/zero 的有限读取

任务 4：只读取 8 个字节

执行：

```bash
head -c 8 /dev/zero | od -An -t u1
zero_status="$?"
printf 'zero read status=%s\n' "$zero_status"
```

预期：

- `od` 显示 8 个数值为 `0` 的字节。
- `zero_status=0`。

重点理解：

- `/dev/zero` 可以持续产生零字节，本身没有普通文件式结尾。
- `head -c 8` 是读取上限，防止命令无限输出。
- 今天只理解受限读取的整体行为，不要求记忆 `od` 参数。

验证标准：

- 输出恰好表示 8 个零字节，命令正常结束。

六、验证 /dev/full 的设备错误

任务 5：写入始终报告空间不足的伪设备

执行：

```bash
printf '%s\n' 'day21 expected failure' > /dev/full
full_status="$?"
printf 'full write status=%s\n' "$full_status"
```

预期：

- 写入提示 `No space left on device` 或对应本地化错误。
- `full_status` 为非 0。

重点理解：

- `/dev/full` 专门用于模拟写入空间不足。
- 即使权限显示可写，也只代表允许发起写入，不保证设备接受数据。
- 该错误是设备行为，不是普通磁盘真的被今天的练习写满。

验证标准：

- 保留设备错误和非 0 状态。
- 能区分权限允许与操作成功。

七、验证设备节点不存在

任务 6：查询明确不存在的练习路径

执行：

```bash
ls -l -- /dev/day21-missing
missing_status="$?"
printf 'missing device status=%s\n' "$missing_status"
```

预期：

- `ls` 提示路径不存在。
- `missing_status` 为非 0。

重点理解：

- 节点不存在时，第一步检查设备路径和名称是否正确。
- 不存在与存在但权限不足是不同情况。
- 不要为了消除错误而使用 `mknod` 创建虚假设备节点。

验证标准：

- 保留不存在错误和非 0 状态。

八、创建设备节点检查脚本

任务 7：为 Robot System Diagnostic Tool 创建项目脚本

执行：

```bash
cd "$HOME/workspace/learn/learn/robot-system-learning/linux"
vim device_node_check.sh
```

在 Vim 中写入下面的完整内容：

```bash
#!/bin/bash

device_path="$1"

if [[ -z "$device_path" ]]; then
    printf '%s\n' '[DEVICE CHECK ERROR] device path is required' >&2
    exit 1
fi

case "$device_path" in
    /dev/*)
        ;;
    *)
        printf '[DEVICE CHECK ERROR] path must be under /dev: %s\n' \
            "$device_path" >&2
        exit 1
        ;;
esac

if [[ ! -e "$device_path" ]]; then
    printf '[DEVICE CHECK ERROR] device node not found: %s\n' \
        "$device_path" >&2
    exit 1
fi

if [[ -c "$device_path" ]]; then
    device_type='character'
elif [[ -b "$device_path" ]]; then
    device_type='block'
else
    printf '[DEVICE CHECK ERROR] path is not a device node: %s\n' \
        "$device_path" >&2
    exit 1
fi

readable='no'
writable='no'
[[ -r "$device_path" ]] && readable='yes'
[[ -w "$device_path" ]] && writable='yes'

printf '[DEVICE FOUND] path=%s type=%s readable=%s writable=%s\n' \
    "$device_path" "$device_type" "$readable" "$writable"
ls -l -- "$device_path"
```

保存后执行：

```bash
bash -n device_node_check.sh
chmod u+x device_node_check.sh
ls -l device_node_check.sh
cat device_node_check.sh
```

脚本整体逻辑：

1. 接收一个设备路径。
2. 缺少路径或路径不在 `/dev/` 下时输出错误并停止。
3. 路径不存在时输出 device node not found。
4. 只接受字符设备或块设备，拒绝目录和普通文件。
5. 读取当前用户是否具有读写权限。
6. 输出路径、设备类型、访问权限和 `ls -l` 结果。

重点理解：

- 脚本只查看元数据，不实际读写设备。
- 找到节点后仍需区分节点类型和当前用户权限。
- readable/writable 只描述权限检查结果，不保证每次设备操作都会成功。
- 本日只理解整体检查顺序，不要求掌握 case 或文件测试语法。

验证标准：

- `bash -n` 没有输出，表示没有发现 Shell 语法错误。
- 权限中 owner 具有 `x`。
- 文件内容与上面的完整脚本一致。

九、验证脚本正常路径

重点理解：

- `/dev/full` 权限检查可以通过，但前面的真实写入仍会失败。

验证标准：

十二、机器人系统中的位置

```text
机器人应用需要访问设备
          ↓
先确认 /dev 设备节点存在
          ↓
检查节点类型和当前用户权限
          ↓
再进行受控的设备功能操作
          ↓
根据不存在、权限或设备错误继续定位
```

重点理解：

- 设备诊断先确认入口是否存在，再看节点类型和权限，最后才验证设备实际行为。
- 节点存在不代表权限足够，权限足够也不代表设备操作一定成功。
- 今天只检查标准伪设备；真实机器人硬件必须使用对应的安全流程，不能随意读写。

验证标准：

- 能按节点存在性、节点类型、权限和设备行为说明整体检查顺序。
