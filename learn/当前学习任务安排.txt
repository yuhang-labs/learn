二、准备 source 实验文件

任务 1：在 `/tmp` 中创建一份同时定义变量和函数的临时文件

执行：

```bash
practice_dir='/tmp/day11-source-practice'
mkdir -p "$practice_dir"
vim "$practice_dir/day11_config.sh"
```

在 Vim 中写入下面的完整内容：

```bash
#!/bin/bash

export DAY11_MODE='diagnostic'

day11_status() {
    echo "[DAY11] mode=$DAY11_MODE"
}
```

保存后执行：

```bash
cat "$practice_dir/day11_config.sh"
bash -n "$practice_dir/day11_config.sh"
chmod +x "$practice_dir/day11_config.sh"
```

预期：

- 文件内容与提供的代码一致。
- `bash -n` 没有语法错误。
- 临时文件具有执行权限。

重点理解：

- 该文件只用于观察执行环境差异，不要求自己编写函数。
- 文件位于 `/tmp`，不提交到 Git。

验证标准：

- 保留文件内容和语法检查的真实输出。

三、直接运行脚本

任务 2：让临时配置文件在子 Shell 中运行

先清理当前 Shell 中可能存在的同名内容，再直接运行：

```bash
unset DAY11_MODE
unset -f day11_status 2>/dev/null

"$practice_dir/day11_config.sh"

printf 'after direct run: %s\n' "${DAY11_MODE:-<empty>}"
type day11_status 2>&1
```

预期：

- `after direct run` 后显示 `<empty>`。
- 当前 Shell 中找不到 `day11_status` 函数。

整体逻辑：

```text
当前 Shell → 启动子 Shell → 子 Shell 定义变量和函数 → 子 Shell 结束
                                                        ↓
                                      改动没有返回当前 Shell
```

重点理解：

- 直接运行脚本时，Shell 启动新的子进程执行它。
- 脚本中的变量和函数只存在于那个子 Shell，子 Shell 结束后，不会回写到当前 Shell。
- 今天只理解这个方向，不考子进程的细节实现。

验证标准：

- 根据实际输出确认直接运行后，当前 Shell 没有获得该变量和函数。

四、使用 source 加载文件

任务 3：让同一份文件在当前 Shell 中执行

执行：

```bash
source "$practice_dir/day11_config.sh"

printf 'after source: %s\n' "$DAY11_MODE"
type day11_status
day11_status
```

预期：

- `after source` 显示 `diagnostic`。
- `type` 明确显示 `day11_status` 是一个函数。
- 调用函数后显示 `[DAY11] mode=diagnostic`。

整体逻辑：

```text
当前 Shell → source 读取文件 → 文件内容在当前 Shell 执行
                                            ↓
                         变量和函数保留在当前 Shell
```

重点理解：

- `source` 不是将文件“复制”到 Shell，而是让当前 Shell 执行文件内容。
- 因为没有用子 Shell 隔离，文件中的变量、函数和其他 Shell 操作都可能改变当前环境。
- 这正是环境配置文件需要 `source` 的原因。

验证标准：

- 根据实际输出确认变量和函数已保留在当前 Shell。

五、加载失败时逐层检查

任务 4：使用不存在的路径复现失败，再根据证据检查

执行：

```bash
source "$practice_dir/missing_config.sh"
printf '%s\n' '[CHECK] current shell is still running'
```

预期：

- `source` 明确提示 `missing_config.sh` 不存在。
- 当前 Shell 没有因这次失败而结束，后续 `[CHECK]` 文字仍能显示。

按下面顺序检查：

```bash
pwd
ls -l "$practice_dir/day11_config.sh"
bash -n "$practice_dir/day11_config.sh"
```

调试逻辑：

1. 先用 `pwd` 确认当前位置，避免把相对路径理解错。
2. 检查要加载的文件是否真实存在。
3. 文件存在时，再检查其 Shell 语法。
4. 最后重新加载，并检查预期变量或函数是否出现。

重点理解：

- 加载失败时不要直接猜 `source` 坏了，先检查路径、文件和语法。
- 不要求记住错误状态码，只要读懂错误文字并确认当前 Shell 仍可继续工作。

验证标准：

- 保留缺失文件的错误文字和后续检查输出。
- 能按路径、文件、语法、加载结果的顺序定位问题。

六、项目实践：加载 robot_env.sh

任务 5：从项目目录之外加载已有环境配置

执行：

```bash
cd /tmp
unset ROBOT_PROJECT_ROOT ROBOT_LOG_DIR

source "$HOME/workspace/learn/learn/robot-system-learning/linux/robot_env.sh"

printf 'project root: %s\n' "$ROBOT_PROJECT_ROOT"
printf 'log directory: %s\n' "$ROBOT_LOG_DIR"
command -v day8_diagnostic_pipeline.sh
day11_status
```

预期：

- 即使当前目录是 `/tmp`，使用正确的完整路径仍能加载 `robot_env.sh`。
- 两个项目环境变量显示正确值。
- Shell 能通过加载后的 `PATH` 找到 `day8_diagnostic_pipeline.sh`。
- 之前通过 `source` 加载的 `day11_status` 函数仍存在，说明这些改动都在同一个当前 Shell 中保留。

整体流程：

1. 当前 Shell 通过完整路径读取 `robot_env.sh`。
2. `robot_env.sh` 的内容在当前 Shell 中执行。
3. 项目变量和更新后的 `PATH` 留在当前 Shell。
4. 后续命令可以立即使用这些配置。

学习要求：

- Day11 直接复用 Day10 已创建的 `robot_env.sh`，不再创建内容重复的项目脚本。
- 不修改 `robot_env.sh`，今天的学习对象是加载方式，不是环境文件内容。
- 不要求了解 `~/.bashrc` 或永久加载。

验证标准：

- 从 `/tmp` 成功加载项目环境。
- 加载后的变量、命令位置和已有函数均符合预期。

七、清理本次临时内容

任务 6：清理 Day11 临时变量和函数

执行：

```bash
unset DAY11_MODE
unset -f day11_status

printf 'after cleanup: %s\n' "${DAY11_MODE:-<empty>}"
type day11_status 2>&1
```

预期：

- `DAY11_MODE` 显示 `<empty>`。
- 当前 Shell 中不再存在 `day11_status` 函数。

重点理解：

- 因为 `source` 直接修改当前 Shell，所以必要时也要在当前 Shell 中清理它加载的临时内容。
- 不要求背清理命令，只要理解改动留在哪个 Shell 中。

验证标准：

- 清理后的真实输出符合预期。
