二、理解 systemd、unit 与 systemctl

任务 1：建立整体概念

```text
unit 文件或系统配置
        ↓ 交给 systemd
systemd 管理服务生命周期和状态
        ↑
systemctl 查询或请求 start / stop
        ↓
状态、MainPID、成功或错误信息
```

重点理解：

- systemd 通常作为系统初始化与服务管理器，负责管理 service 等 unit。
- service unit 描述“如何启动和管理一个服务”，服务启动后通常对应一个或多个进程。
- `systemctl` 是用户与 systemd 交互的工具，负责发送查询或控制请求。
- unit 文件是管理配置，不是运行中的服务进程。
- 今天只理解输入、管理对象、状态输出和验证链路，不学习内部依赖算法。

验证标准：

- 后续能把 unit 文件、systemd、systemctl、服务进程和状态证据连成一条完整链路。

三、确认当前 systemd 环境

任务 2：检查系统管理器和用户管理器是否可用

执行：

```bash
ps -p 1 -o pid,comm,args
systemctl --version | head -n 1
systemctl is-system-running
systemctl --user is-system-running
```

结果判断：

- PID 1 的命令名通常是 `systemd`，说明当前系统由 systemd 初始化和管理。
- `systemctl --version` 显示当前 systemd 版本。
- `systemctl is-system-running` 可能显示 `running`、`degraded` 或其他真实状态，应如实记录。
- `systemctl --user is-system-running` 能返回用户管理器状态时，才继续用户服务启停实验。
- 如果出现 `Failed to connect to bus`，记录错误并停止任务 4 至任务 7，向 AI 反馈；不要使用 `sudo` 或改动系统服务。

重点理解：

- 系统级 systemd 和当前用户的 user manager 管理范围不同。
- Day16 使用 `--user`，把实验范围限制在当前用户会话。

验证标准：

- 保留 PID 1、systemd 版本、系统状态和 user manager 状态的真实输出。

四、查看服务与 unit 文件快照

任务 3：比较当前运行状态与自动启动配置

执行：

```bash
printf '%s\n' '[RUNNING SERVICES]'
systemctl list-units --type=service --state=running --no-pager | head -n 15

printf '%s\n' '[SERVICE UNIT FILES]'
systemctl list-unit-files --type=service --no-pager | head -n 15
```

重点理解：

- `list-units` 主要展示 systemd 当前已加载的 unit 及其运行状态。
- `list-unit-files` 主要展示磁盘上的 unit 文件及其启用状态。
- `active` 描述当前运行状态；`enabled` 描述是否配置为随相应目标自动启动。
- 服务可以当前 active 但不一定 enabled，也可以 enabled 但当前没有运行，两者不能混为一谈。

验证标准：

- 保留两组前15行真实输出。
- 能根据输出区分“当前状态”和“自动启动配置”。

五、创建 Day16 项目 unit

任务 4：在 Linux 项目中创建安全的用户服务配置

执行：

```bash
cd "$HOME/workspace/learn/learn/robot-system-learning/linux"
vim day16-practice.service
```

在 Vim 中写入下面的完整内容：

```ini
[Unit]
Description=Day16 safe systemd user service practice

[Service]
Type=simple
ExecStart=/usr/bin/sleep infinity
```

保存后执行：

```bash
project_unit="$PWD/day16-practice.service"

systemd-analyze --user verify "$project_unit"
cat "$project_unit"
git -C "$HOME/workspace/learn/learn" status --short -- robot-system-learning/linux/day16-practice.service
```

重点理解：

- `[Unit]` 保存该 unit 的说明信息。
- `[Service]` 描述服务进程如何启动。
- 这里使用 `sleep infinity` 只是创建一个持续运行、可安全停止的练习进程。
- unit 文件位于项目中，后续由 Git 管理；它本身存在不代表服务已经运行。
- 不要求记住 unit 文件字段或语法。

验证标准：

- `systemd-analyze` 没有报告 unit 语法错误。
- 文件内容与给定内容一致。
- Git 显示 `day16-practice.service` 是新增文件。

六、加载 unit 并检查初始状态

任务 5：把项目 unit 链接到用户管理器

执行：

```bash
systemctl --user link "$project_unit"
systemctl --user daemon-reload

systemctl --user show day16-practice.service \
  -p LoadState -p ActiveState -p SubState -p UnitFileState

systemctl --user status day16-practice.service --no-pager
```

预期：

- `LoadState=loaded` 表示 user manager 已读取该 unit。
- 尚未启动时，`ActiveState` 应为 `inactive`。
- `UnitFileState` 可能显示 `linked`，表示用户管理器通过链接找到项目中的 unit 文件。
- `status` 在 inactive 状态可能返回非零结果；以文字状态为准，不要求记忆状态码。

重点理解：

- 修改或新增 unit 后，`daemon-reload` 让 systemd 重新读取配置。
- 已加载不等于正在运行。

验证标准：

- 保留加载状态、活动状态和 `status` 的真实输出。

七、启动服务并关联进程

任务 6：使用 systemctl start 启动用户服务

执行：

```bash
systemctl --user start day16-practice.service

systemctl --user status day16-practice.service --no-pager
systemctl --user is-active day16-practice.service
systemctl --user show day16-practice.service \
  -p LoadState -p ActiveState -p SubState -p MainPID

main_pid="$(systemctl --user show day16-practice.service -p MainPID --value)"
printf 'service MainPID: %s\n' "$main_pid"
ps -p "$main_pid" -o pid,ppid,user,stat,etime,cmd
```

预期：

- 服务状态显示 `active (running)`，`is-active` 输出 `active`。
- `MainPID` 是大于0的进程 PID。
- `ps` 显示相同 PID，并且运行用户是当前用户，命令包含 `sleep infinity`。

整体逻辑：

```text
systemctl --user start
          ↓
user systemd 读取 unit 的 ExecStart
          ↓
启动 sleep 练习进程并记录 MainPID
          ↓
status / show / ps 从不同层面确认结果
```

验证标准：

- 保留 `active`、MainPID 和对应 `ps` 进程行。

八、停止服务并回归验证

任务 7：使用 systemctl stop 停止用户服务

执行：

```bash
systemctl --user stop day16-practice.service

systemctl --user is-active day16-practice.service ||
  printf '%s\n' '[EXPECTED] day16 practice service is inactive'

systemctl --user show day16-practice.service \
  -p LoadState -p ActiveState -p SubState -p MainPID

ps -p "$main_pid" -o pid,ppid,user,stat,etime,cmd ||
  printf '%s\n' '[EXPECTED] previous MainPID is no longer running'
```

预期：

- 服务状态变为 `inactive`，MainPID 变为 `0`。
- 启动时保存的原 MainPID 不再对应运行中的练习进程。
- 这说明 `stop` 请求已生效；不能只凭命令没有报错就判断服务停止。

验证标准：

- 保留停止后的 unit 状态和原 MainPID 消失证据。

九、验证 unit 不存在的异常场景

任务 8：查询一个明确不存在的练习 unit

执行：

```bash
systemctl --user status day16-missing.service --no-pager

systemctl --user show day16-missing.service \
  -p LoadState -p ActiveState -p SubState
```

预期：

- `status` 提示找不到 `day16-missing.service`。
- `show` 中 `LoadState` 显示 `not-found`。

重点理解：

- unit 不存在与 unit 存在但 inactive 是两种不同状态。
- `not-found` 时先检查 unit 名称和文件位置，再考虑 `daemon-reload`，不能直接猜服务进程故障。
- 异常输出本身就是诊断证据，不要求记忆返回码。

验证标准：

- 保留缺失 unit 的错误和 `LoadState` 证据。

十、只读查看 SSH 与 CAN 相关服务

任务 9：完成固定计划中的相关服务检查

执行：

```bash
printf '%s\n' '[SSH/CAN UNIT FILE MATCHES]'
systemctl list-unit-files --type=service --no-pager |
  grep -Ei 'ssh|sshd|can|socketcan' ||
  printf '%s\n' '[INFO] no matching SSH/CAN service unit files found'

printf '%s\n' '[SSH/CAN LOADED UNIT MATCHES]'
systemctl list-units --type=service --all --no-pager |
  grep -Ei 'ssh|sshd|can|socketcan' ||
  printf '%s\n' '[INFO] no matching loaded SSH/CAN services found'

printf '%s\n' '[SSH COMMON UNIT STATES]'
systemctl show ssh.service sshd.service \
  -p Id -p LoadState -p ActiveState -p SubState -p UnitFileState --no-pager
```

结果判断：

- 有匹配时，如实记录 unit 名称、加载状态和活动状态。
- `LoadState=not-found` 表示对应名称的 unit 文件没有被找到，不等于 SSH 软件一定未安装。
- 没有 CAN service 匹配，不等于系统不支持 CAN；CAN 也可能由网络配置、自定义 unit 或其他工具管理。
- 这里只查询，不对任何真实 SSH、CAN 或系统服务执行状态修改。

验证标准：

- 保留真实匹配结果或无匹配提示。
- 没有对真实服务执行启停或配置修改。

十二、服务问题的基础诊断顺序

任务 11：形成 systemd 服务层面的取证流程

```text
确认 unit 名称与管理范围（系统级或 --user）
                    ↓
检查 LoadState，确认配置是否被找到并加载
                    ↓
检查 ActiveState / SubState，确认当前状态
                    ↓
查看 status 中的 MainPID 和错误信息
                    ↓
需要时检查对应进程
                    ↓
做最小修改后重新查询状态
```

重点理解：

- 先确认对象和管理范围，再判断运行状态。
- `not-found`、`inactive` 和 `active` 表示不同问题层级。
- Day16 先使用状态和进程证据；服务日志的系统学习留到 Day17。

验证标准：

- 能按 unit 名称、加载状态、活动状态、MainPID 和回归查询的顺序说明过程。
