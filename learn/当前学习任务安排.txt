二、理解 dmesg 与设备事件

任务 1：建立整体概念

```text
设备或控制器发生事件
          ↓
内核识别并处理事件
          ↓
内核把相关消息写入环形缓冲区
          ↓
dmesg 读取当前仍保留的内核消息
          ↓
按时间顺序检查发现、身份和驱动处理
```

重点理解：

- `dmesg` 是读取内核消息的工具，不是主动检测或修复设备的命令。
- 内核环形缓冲区容量有限，旧消息可能被新消息覆盖；它不是永久、完整的历史档案。
- 一组设备事件通常要按前后顺序阅读，不能只凭单独一行判断全过程。
- 内核记录设备事件，只证明内核在对应时刻观察或处理了某件事，不保证当前设备仍在，也不保证应用功能正常。
- 普通用户是否能读取内核缓冲区由系统安全策略决定。

验证标准：

- 能按“设备事件 → 内核处理 → 环形缓冲区 → `dmesg` 读取”的顺序解释。

三、确认工具和读取权限

任务 2：只探测一次 `dmesg` 读取结果

执行：

```bash
command -v dmesg
tool_status="$?"
printf 'dmesg tool status=%s\n' "$tool_status"

dmesg --version

dmesg_output="$(dmesg --color=never 2>&1)"
dmesg_status="$?"
printf 'dmesg read status=%s\n' "$dmesg_status"

if [[ "$dmesg_status" -eq 0 ]]; then
    printf '%s\n' '[DMESG READ OK] kernel messages are readable'
else
    printf '%s\n' "$dmesg_output"
fi
```

结果判断：

- `tool_status=0` 只表示系统安装了 `dmesg`。
- `dmesg_status=0` 表示当前用户成功读取内核缓冲区，进入“实际日志路径”。
- 非 0 状态并显示“不允许的操作”或 `Operation not permitted`，进入“权限受限路径”。
- 工具存在与日志可读是两个不同条件。

安全要求：

- 不把变量 `dmesg_output` 的全部内容打印或写入仓库。
- 不使用 `sudo dmesg`，不修改系统安全设置来绕过限制。

验证标准：

- 保留命令路径、版本、读取状态，以及成功提示或原始权限错误。

四、实际日志路径：过滤设备相关事件

任务 3：仅在 `dmesg_status=0` 时执行

执行：

```bash
device_lines="$(printf '%s\n' "$dmesg_output" |
  grep -Ei -- 'usb|xhci|hid' |
  grep -vi -F -- 'SerialNumber' |
  tail -n 20)"

if [[ -n "$device_lines" ]]; then
    printf '%s\n' "$device_lines"
else
    printf '%s\n' '[NO MATCH] no retained USB-related kernel message'
fi
```

记录要求：

- 最多保留输出的 20 行，不粘贴完整 `dmesg`。
- 从相邻行中选择一小段，按实际顺序写出内核先后观察到了什么。
- 如果过滤结果为空，只记录 `[NO MATCH]`，不能据此断言系统从未发生 USB 事件。

常见字段：

- 方括号中的数字通常表示相对本次启动的时间位置。
- `usb 1-8` 一类内容表示内核使用的 USB 连接路径，不等同于 `lsusb` 的 Bus/Device 稳定身份。
- `new ... USB device` 表示发现设备事件。
- `idVendor`、`idProduct` 表示设备报告的厂商和产品 ID。
- `Product`、`Manufacturer` 是设备提供的描述信息，可能缺失。
- `xhci_hcd`、`usbhid`、`hid-generic` 等名称表明相应内核组件参与处理。

验证标准：

- 只保留受限结果，并能按输出实际顺序说明至少两个连续步骤。

五、权限受限路径：读取教学事件序列

任务 4：仅在 `dmesg_status` 非 0 时使用

下面是教学样例，不是你的电脑实际日志：

```text
[教学样例，非本机日志]
[    1.100000] usb 1-4: new full-speed USB device number 2 using xhci_hcd
[    1.240000] usb 1-4: New USB device found, idVendor=1234, idProduct=5678
[    1.250000] usb 1-4: Product: Example Input Device
[    1.300000] hid-generic 0003:1234:5678.0001: input,hidraw0: USB HID v1.11 Device
```

按顺序填写：

```text
第 1 步：
第 2 步：
第 3 步：
第 4 步：
连接路径：
VID:PID：
参与处理的内核组件：
```

正确的整体顺序应包含：

1. 主机控制器发现一个新 USB 设备。
2. 内核取得 `idVendor=1234` 和 `idProduct=5678`。
3. 内核取得产品描述 Example Input Device。
4. HID 相关组件继续处理该设备接口。

记录要求：

- 先保留你自己的权限错误和状态。
- 明确写出“以下分析来自教学样例，不是本机日志”。
- 不把样例 ID、路径或设备名称写成自己的真实设备信息。

验证标准：

- 能按时间顺序读出教学事件，同时保留本机实际读取受限的结论。

六、连接 Day22 与 Day23 的证据

任务 5：理解当前快照与事件过程

```text
Day22：lsusb
当前查询时刻有哪些 USB 设备被枚举

Day23：dmesg
当前缓冲区仍保留了哪些内核事件消息
```

重点理解：

- `lsusb` 是当前枚举结果的快照，Bus 和 Device 反映查询时的分配结果。
- `dmesg` 中相邻消息可以展示内核处理事件的先后过程，但旧消息可能已被覆盖，也可能因权限无法读取。
- `lsusb` 当前找到设备，不保证对应的早期事件仍留在缓冲区。
- `dmesg` 中曾出现设备，也不保证设备当前仍连接。
- 两种证据都不能代替应用层的真实通信验证。

验证标准：

- 后续回答能准确说明快照、事件顺序以及各自的证据边界。

七、创建设备事件检查脚本

任务 6：创建 `device_event_check.sh`

执行：

```bash
cd "$HOME/workspace/learn/learn/robot-system-learning/linux"
vim device_event_check.sh
```

在 Vim 中写入下面的完整内容：

```bash
#!/bin/bash

keyword="$1"

if [[ -z "$keyword" ]]; then
    printf '%s\n' '[DEVICE EVENT ERROR] keyword is required' >&2
    exit 1
fi

case "$keyword" in
    usb|xhci|hid|day23-no-match)
        ;;
    *)
        printf '[DEVICE EVENT ERROR] unsupported keyword: %s\n' \
            "$keyword" >&2
        exit 1
        ;;
esac

kernel_output="$(dmesg --color=never 2>&1)"
dmesg_status="$?"

if [[ "$dmesg_status" -ne 0 ]]; then
    printf '%s\n' '[DEVICE EVENT ERROR] kernel messages are not readable' >&2
    printf '%s\n' "$kernel_output" >&2
    exit 2
fi

match_output="$(printf '%s\n' "$kernel_output" |
  grep -i -F -- "$keyword" |
  grep -vi -F -- 'SerialNumber' |
  tail -n 20)"

if [[ -z "$match_output" ]]; then
    printf '[DEVICE EVENT ERROR] no retained event matched: %s\n' \
        "$keyword" >&2
    exit 1
fi

printf '[DEVICE EVENT FOUND] keyword=%s\n' "$keyword"
printf '%s\n' "$match_output"
```

保存后执行：

```bash
bash -n device_event_check.sh
chmod u+x device_event_check.sh
ls -l device_event_check.sh
cat device_event_check.sh
```

脚本整体逻辑：

1. 拒绝空输入和不支持的关键词。
2. 读取一次内核环形缓冲区。
3. 读取受限时保留原始错误并返回状态 `2`。
4. 读取成功后只过滤允许的关键词，排除 `SerialNumber`，最多输出 20 行。
5. 有匹配返回 `0`，没有保留匹配事件返回 `1`。

验证标准：

- `bash -n` 没有输出。
- owner 具有执行权限。
- 脚本内容与上面的完整版本一致。

九、验证与当前权限相符的脚本分支

任务 8：根据任务 2 的读取状态选择一条路径

如果 `dmesg_status=0`，执行：

```bash
./device_event_check.sh usb
usb_event_status="$?"
printf 'USB event status=%s\n' "$usb_event_status"

./device_event_check.sh day23-no-match
no_match_status="$?"
printf 'event no-match status=%s\n' "$no_match_status"
```

预期：

- 当前缓冲区保留 USB 消息时，第一项输出 `[DEVICE EVENT FOUND]` 和最多 20 行，状态为 `0`。
- `day23-no-match` 输出 no retained event matched，状态为 `1`。
- 如果第一项没有匹配，也可能返回 `1`；这只表示当前缓冲区没有保留匹配消息。

如果 `dmesg_status` 非 0，执行：

```bash
./device_event_check.sh usb
environment_status="$?"
printf 'dmesg environment status=%s\n' "$environment_status"
```

预期：

- 输出 kernel messages are not readable 和原始权限错误。
- `environment_status=2`。
- 脚本没有把权限受限误报成没有匹配事件。

验证标准：

- 输入错误与环境错误被区分；读取成功环境再区分有匹配和无匹配。
